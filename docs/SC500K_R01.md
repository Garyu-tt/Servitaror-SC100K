# SC500K R01: hippocampus-inspired full-machine prototype

An independent branch from R25 preserves the ongoing SC100K Linux boot. This prototype replaces guest RAM with recurrent dual-rail spikes, persists a miniature disk as Q4 synaptic coefficients (1/7), and adds an 8x8 monochrome parallel visual region. Two-level weighted address selection is inspired by hippocampal pattern separation, not a reconstruction of biological hippocampal circuitry. All address rows are evaluated; no host-indexed payload read or write. MMIO routes disk and graphics commands, and host schedules clock phases and persists synaptic state as NPZ. No shadow guest bytearray during execution.

Estimated logical-cell allocation, assuming reuse of disk read/program rail cells across phases: full prior core 123110, 1024-byte RAM 331280, 128-byte synaptic disk 42090, 64-pixel visual region 3370; total 499850. These are engineering estimates, not an instantiated unified GENESIS graph or trained connectome. The fixture executes the RV32I subset, not the entire prior privileged core. Full Linux requires radically denser exact storage; 1 KiB RAM is not enough. Physical host memory, disk and CPU remain necessary to simulate/checkpoint the network.

Local PASS: all 256 addresses, 384 randomized/retention read comparisons, five ablations, 25 actual guest instructions and 64 neural ALU calls. Firmware restores Q4 disk coefficients, copies program via neural read/write to recurrent RAM, then guest fetches and executes from that RAM. Guest writes/reads disk MMIO and draws/erases via graphics MMIO; final frame is an 8x8 outlined rectangle. Disk word 31 persists as 42 after restore. No host instruction execution fallback. Run `python neural_hippocampus_r27.py --build-dir /tmp/sc500k-native` and optionally `--disk-checkpoint /tmp/sc500k-synapses.npz`. Checkpoint binary retained locally only. SC100K R26 separately reached 663401 real Linux instructions; no Linux boot on SC500K yet. Next: scalable neural memory, independent exactness tests, unified graph and privileged board integration. Supports #9 and #12.
